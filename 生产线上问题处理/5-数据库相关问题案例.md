# 生产问题案例 - 数据库相关（案例 29-36）

## 案例29: 慢查询导致数据库 CPU 飙高

### 问题现象
- 数据库 CPU 使用率 100%
- 应用接口响应慢
- 大量慢查询日志

### 排查过程
```bash
# 查看慢查询日志
tail -f /var/log/mysql/slow.log

# 查看正在执行的查询
mysql> SHOW PROCESSLIST;

# 查看慢查询统计
mysql> SHOW GLOBAL STATUS LIKE 'Slow_queries';

# 分析慢查询
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log
```

### 根因分析
```sql
-- 问题 SQL
SELECT * FROM orders o
LEFT JOIN users u ON o.user_id = u.id
WHERE o.status = 1
ORDER BY o.create_time DESC
LIMIT 1000000, 10;

-- EXPLAIN 分析
EXPLAIN SELECT * FROM orders o
LEFT JOIN users u ON o.user_id = u.id
WHERE o.status = 1
ORDER BY o.create_time DESC
LIMIT 1000000, 10;

-- type: ALL (全表扫描)
-- rows: 10000000
-- Using filesort
```

### 解决方案
```sql
-- 方案1: 添加索引
ALTER TABLE orders ADD INDEX idx_status_create_time (status, create_time);
ALTER TABLE orders ADD INDEX idx_user_id (user_id);

-- 方案2: 优化分页
-- 使用游标分页
SELECT * FROM orders o
LEFT JOIN users u ON o.user_id = u.id
WHERE o.status = 1 AND o.id > 1000000
ORDER BY o.id
LIMIT 10;

-- 方案3: 延迟关联
SELECT o.*, u.name, u.email
FROM (
    SELECT id FROM orders
    WHERE status = 1
    ORDER BY create_time DESC
    LIMIT 1000000, 10
) t
LEFT JOIN orders o ON t.id = o.id
LEFT JOIN users u ON o.user_id = u.id;

-- 方案4: 使用覆盖索引
SELECT o.id, o.status, o.create_time
FROM orders o
WHERE o.status = 1
ORDER BY o.create_time DESC
LIMIT 10;
```

## 案例30: 锁等待导致接口超时

### 问题现象
- 接口超时
- 数据库锁等待严重
- 事务执行时间长

### 排查过程
```sql
-- 查看锁等待
SELECT * FROM information_schema.INNODB_LOCK_WAITS;

-- 查看当前锁
SELECT * FROM information_schema.INNODB_LOCKS;

-- 查看长事务
SELECT * FROM information_schema.INNODB_TRX
WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 60;

-- 查看锁等待详情
SELECT
    r.trx_id waiting_trx_id,
    r.trx_mysql_thread_id waiting_thread,
    r.trx_query waiting_query,
    b.trx_id blocking_trx_id,
    b.trx_mysql_thread_id blocking_thread,
    b.trx_query blocking_query
FROM information_schema.INNODB_LOCK_WAITS w
INNER JOIN information_schema.INNODB_TRX b ON b.trx_id = w.blocking_trx_id
INNER JOIN information_schema.INNODB_TRX r ON r.trx_id = w.requesting_trx_id;
```

### 根因分析
```java
// 问题代码: 大事务，锁持有时间长
@Transactional
public void processOrder(Long orderId) {
    // 1. 查询订单（加锁）
    Order order = orderRepository.findById(orderId).orElseThrow();
    
    // 2. 调用外部服务（耗时操作）
    paymentService.processPayment(order);  // RPC 调用，可能超时
    
    // 3. 更新订单状态
    order.setStatus("PAID");
    orderRepository.save(order);
    
    // 4. 发送消息
    messageService.sendNotification(order);
    
    // 整个事务持有锁的时间很长
}
```

### 解决方案
```java
// 方案1: 缩小事务范围
public void processOrder(Long orderId) {
    // 1. 查询订单（不加锁）
    Order order = orderRepository.findById(orderId).orElseThrow();
    
    // 2. 调用外部服务（在事务外）
    paymentService.processPayment(order);
    
    // 3. 更新订单状态（短事务）
    updateOrderStatus(orderId, "PAID");
    
    // 4. 发送消息（异步）
    messageService.sendNotificationAsync(order);
}

@Transactional
public void updateOrderStatus(Long orderId, String status) {
    Order order = orderRepository.findById(orderId).orElseThrow();
    order.setStatus(status);
    orderRepository.save(order);
}

// 方案2: 使用乐观锁
@Version
private Long version;

// 方案3: 设置锁超时
SET innodb_lock_wait_timeout = 10;
```

## 案例31: 连接池耗尽

### 问题现象
- 报错 "Cannot get a connection, pool error Timeout waiting for idle object"
- 数据库连接数达到上限
- 应用无法处理新请求

### 排查过程
```sql
-- 查看数据库连接数
SHOW STATUS LIKE 'Threads_connected';
SHOW VARIABLES LIKE 'max_connections';

-- 查看连接详情
SELECT * FROM information_schema.PROCESSLIST;
```

### 根因分析
```java
// 问题代码: 连接泄漏
public void queryData() {
    Connection conn = null;
    try {
        conn = dataSource.getConnection();
        // 执行查询
        // 异常时未归还连接
    } catch (Exception e) {
        log.error("查询失败", e);
        // 忘记归还连接
    }
    // finally 中未关闭连接
}
```

### 解决方案
```java
// 方案1: 使用 try-with-resources
public void queryData() {
    try (Connection conn = dataSource.getConnection();
         PreparedStatement ps = conn.prepareStatement("SELECT * FROM users");
         ResultSet rs = ps.executeQuery()) {
        // 处理结果
    }
}

// 方案2: 使用 JdbcTemplate
@Autowired
private JdbcTemplate jdbcTemplate;

public List<User> queryUsers() {
    return jdbcTemplate.query("SELECT * FROM users", new UserRowMapper());
}

// 方案3: 配置连接池监控
HikariConfig config = new HikariConfig();
config.setLeakDetectionThreshold(60000);  // 泄漏检测 60秒
config.setMaximumPoolSize(20);
config.setMinimumIdle(5);
```

## 案例32: 主从延迟导致数据不一致

### 问题现象
- 写入主库后立即读从库，数据不一致
- 用户反馈刚创建的数据看不到
- 业务逻辑判断错误

### 排查过程
```sql
-- 查看主从延迟
SHOW SLAVE STATUS\G

-- Seconds_Behind_Master: 300 (延迟300秒)

-- 查看从库状态
SHOW PROCESSLIST;
```

### 根因分析
```
问题原因:
1. 主库写入量大，从库来不及同步
2. 从库硬件性能差
3. 网络延迟
4. 大事务阻塞复制

# 主从延迟 300 秒意味着:
# - 写入主库的数据，300 秒后才能在从库读到
```

### 解决方案
```java
// 方案1: 写后读走主库
public void createOrder(Order order) {
    // 写主库
    orderRepository.save(order);
    
    // 读主库（强制）
    Order saved = orderRepository.findById(order.getId()).orElseThrow();
}

// 使用 Spring 的 @DS 注解（dynamic-datasource）
@DS("master")  // 强制走主库
public Order getOrderFromMaster(Long id) {
    return orderRepository.findById(id).orElseThrow();
}

// 方案2: 使用 Canal 订阅 binlog
// 实时同步到其他数据源

// 方案3: 使用 Redis 缓存
// 写入后立即更新缓存
public void createOrder(Order order) {
    orderRepository.save(order);
    redisTemplate.opsForValue().set("order:" + order.getId(), order, 10, TimeUnit.MINUTES);
}
```

## 案例33: 大事务导致锁等待

### 问题现象
- 事务执行时间长
- 锁等待严重
- 并发性能差

### 排查过程
```sql
-- 查看长事务
SELECT * FROM information_schema.INNODB_TRX
WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 10;

-- 查看锁等待
SELECT * FROM information_schema.INNODB_LOCK_WAITS;
```

### 根因分析
```java
// 问题代码: 大事务包含 RPC 调用
@Transactional
public void processLargeTransaction() {
    // 1. 批量插入
    for (int i = 0; i < 10000; i++) {
        Order order = new Order();
        orderRepository.save(order);
    }
    
    // 2. 调用外部服务（耗时）
    externalService.process();
    
    // 3. 更新库存
    inventoryService.updateStock();
    
    // 事务持续时间长，锁持有时间长
}
```

### 解决方案
```java
// 方案1: 拆分大事务
public void processLargeTransaction() {
    // 批量插入（独立事务）
    batchInsertOrders();
    
    // 调用外部服务（无事务）
    externalService.process();
    
    // 更新库存（独立事务）
    inventoryService.updateStock();
}

@Transactional
public void batchInsertOrders() {
    // 批量插入逻辑
}

// 方案2: 使用批量插入
@Transactional
public void batchInsert() {
    List<Order> orders = new ArrayList<>();
    for (int i = 0; i < 10000; i++) {
        orders.add(new Order());
    }
    orderRepository.saveAll(orders);  // 批量插入
}

// 方案3: 设置事务超时
@Transactional(timeout = 30)  // 30秒超时
public void processWithTimeout() {
    // 业务逻辑
}
```

## 案例34: 索引失效导致全表扫描

### 问题现象
- 查询变慢
- EXPLAIN 显示全表扫描
- 索引存在但未使用

### 排查过程
```sql
-- EXPLAIN 分析
EXPLAIN SELECT * FROM users WHERE YEAR(create_time) = 2024;

-- type: ALL (全表扫描)
-- key: NULL (未使用索引)
```

### 根因分析
```sql
-- 问题 SQL: 对索引列使用函数
SELECT * FROM users WHERE YEAR(create_time) = 2024;

-- 问题 SQL: 隐式类型转换
SELECT * FROM users WHERE phone = 13800138000;
-- phone 是 varchar，传入 int

-- 问题 SQL: 左模糊
SELECT * FROM users WHERE name LIKE '%张';
```

### 解决方案
```sql
-- 方案1: 改写 SQL（避免函数）
SELECT * FROM users
WHERE create_time >= '2024-01-01'
  AND create_time < '2025-01-01';

-- 方案2: 类型匹配
SELECT * FROM users WHERE phone = '13800138000';

-- 方案3: 右模糊
SELECT * FROM users WHERE name LIKE '张%';

-- 方案4: 使用覆盖索引
SELECT id, name, email FROM users WHERE name LIKE '张%';
```

## 案例35: 死锁导致事务回滚

### 问题现象
- 事务偶发回滚
- 日志显示死锁
- 并发场景出现

### 排查过程
```sql
-- 查看死锁日志
SHOW ENGINE INNODB STATUS;

-- 查看最近的死锁
-- LATEST DETECTED DEADLOCK 部分
```

### 根因分析
```java
// 问题代码: 不同顺序加锁
// 事务 A
@Transactional
public void processA() {
    lock(1);  // 锁定资源 1
    lock(2);  // 等待资源 2（被事务 B 锁定）
}

// 事务 B
@Transactional
public void processB() {
    lock(2);  // 锁定资源 2
    lock(1);  // 等待资源 1（被事务 A 锁定）
}
```

### 解决方案
```java
// 方案1: 统一加锁顺序
public void processA() {
    lock(1);  // 先锁小 ID
    lock(2);
}

public void processB() {
    lock(1);  // 先锁小 ID
    lock(2);
}

// 方案2: 使用乐观锁
@Version
private Long version;

// 方案3: 设置锁超时
SET innodb_lock_wait_timeout = 10;

// 方案4: 使用 SELECT ... FOR UPDATE NOWAIT
SELECT * FROM orders WHERE id = 1 FOR UPDATE NOWAIT;
```

## 案例36: 分页查询深度分页性能问题

### 问题现象
- 前几页查询快
- 后面页查询慢
- 深度分页超时

### 排查过程
```sql
-- 深度分页 SQL
SELECT * FROM orders ORDER BY id LIMIT 1000000, 10;

-- EXPLAIN
-- type: ALL
-- rows: 1000000
-- Using filesort
```

### 根因分析
```
问题原因:
1. LIMIT offset, size 需要扫描 offset + size 行
2. offset 越大，扫描行数越多
3. 深度分页性能急剧下降
```

### 解决方案
```sql
-- 方案1: 使用游标分页（推荐）
-- 第一页
SELECT * FROM orders ORDER BY id LIMIT 10;
-- 下一页（使用上一页最后一条的 id）
SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 10;

-- 方案2: 延迟关联
SELECT o.*
FROM orders o
INNER JOIN (
    SELECT id FROM orders ORDER BY id LIMIT 1000000, 10
) t ON o.id = t.id;

-- 方案3: 使用覆盖索引
SELECT id, status, create_time
FROM orders
WHERE status = 1
ORDER BY create_time DESC
LIMIT 1000000, 10;

-- 方案4: 业务限制分页深度
-- 只允许查询前 100 页
```

## 数据库问题预防 Checklist

```
数据库问题预防:

□ 索引优化:
  - 定期分析慢查询
  - 添加必要的索引
  - 避免索引失效写法
  - 使用 EXPLAIN 验证

□ 事务优化:
  - 保持事务短小
  - 避免 RPC 调用在事务中
  - 设置合理的隔离级别
  - 使用乐观锁

□ 连接管理:
  - 使用连接池
  - 配置合理的连接数
  - 开启泄漏检测
  - 及时关闭连接

□ 监控告警:
  - 慢查询监控
  - 连接数监控
  - 锁等待监控
  - 主从延迟监控
```
