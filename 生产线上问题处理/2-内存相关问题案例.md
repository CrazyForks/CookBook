# 生产问题案例 - 内存相关（案例 9-16）

## 案例9: 大 List 导致 OOM

### 问题现象
- 服务启动后内存持续增长
- 最终抛出 OutOfMemoryError: Java heap space
- 重启后问题重复出现

### 排查过程
```bash
# 1. 查看堆内存使用
jstat -gcutil <pid> 1000

# 2. 生成堆转储
jmap -dump:format=b,file=heap.hprof <pid>

# 3. 使用 MAT 分析
# 查找 Dominator Tree
# 找到占用内存最大的对象
```

### 根因分析
```java
// 问题代码: 查询所有数据到内存
public List<Order> getAllOrders() {
    // 查询所有订单，没有分页
    return orderRepository.findAll();  // 100万条数据加载到内存
}

// 每个 Order 对象约 1KB
// 100万条 = 1GB 内存
```

### 解决方案
```java
// 方案1: 分页查询
public void processAllOrders() {
    int page = 0;
    int pageSize = 1000;
    Page<Order> orders;
    
    do {
        orders = orderRepository.findAll(PageRequest.of(page, pageSize));
        processOrders(orders.getContent());
        page++;
    } while (orders.hasNext());
}

// 方案2: 流式查询
@Transactional(readOnly = true)
public void processAllOrders() {
    try (Stream<Order> stream = orderRepository.streamAll()) {
        stream.forEach(this::processOrder);
    }
}

// 方案3: 使用 Scroll 分页（大数据量）
public void processAllOrders() {
    ScrollPosition scrollPosition = ScrollPosition.offset();
    Window<Order> window;
    
    do {
        window = orderRepository.findBy(
            scrollPosition,
            q -> q.as(Order.class).limit(1000)
        );
        processOrders(window.getContent());
        scrollPosition = window.positionAt(window.size() - 1);
    } while (window.hasNext());
}
```

## 案例10: 缓存未设置过期时间导致 OOM

### 问题现象
- 服务运行一周后 OOM
- 重启后恢复，一周后再次 OOM
- 内存持续增长

### 排查过程
```bash
# 使用 MAT 分析堆转储
# 查找占用内存最多的集合对象
# 发现大量缓存对象未过期

# Histogram 查看对象数量
# com.example.cache.CacheEntry  5,000,000 个
```

### 根因分析
```java
// 问题代码: 本地缓存未设置过期时间
public class LocalCache {
    private static final Map<String, Object> CACHE = new HashMap<>();
    
    public void put(String key, Object value) {
        CACHE.put(key, value);  // 永不过期
    }
    
    public Object get(String key) {
        return CACHE.get(key);
    }
}

// 缓存持续增长，最终 OOM
```

### 解决方案
```java
// 方案1: 使用 Guava Cache（推荐）
LoadingCache<String, Object> cache = CacheBuilder.newBuilder()
    .maximumSize(10000)           // 最大条目数
    .expireAfterWrite(10, TimeUnit.MINUTES)  // 写入后过期
    .expireAfterAccess(5, TimeUnit.MINUTES)  // 访问后过期
    .removalListener(notification -> {
        // 移除时的回调
    })
    .build(new CacheLoader<String, Object>() {
        @Override
        public Object load(String key) {
            return loadFromDB(key);
        }
    });

// 方案2: 使用 Caffeine（推荐）
Cache<String, Object> cache = Caffeine.newBuilder()
    .maximumSize(10000)
    .expireAfterWrite(Duration.ofMinutes(10))
    .build();

// 方案3: 使用 Redis（分布式缓存）
@Autowired
private RedisTemplate<String, Object> redisTemplate;

// 方案4: 使用 LinkedHashMap 实现 LRU
public class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int maxSize;
    
    public LRUCache(int maxSize) {
        super(16, 0.75f, true);  // accessOrder = true
        this.maxSize = maxSize;
    }
    
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > maxSize;
    }
}
```

## 案例11: 数据库查询未分页导致 OOM

### 问题现象
- 导出功能触发 OOM
- 查询大量数据时报错
- 内存瞬间飙升

### 排查过程
```bash
# 查看日志
tail -f application.log | grep -i "OutOfMemory"

# 日志信息:
# java.lang.OutOfMemoryError: Java heap space
#     at java.util.Arrays.copyOf(Arrays.java:3236)
#     at java.util.ArrayList.grow(ArrayList.java:267)
#     at java.util.ArrayList.add(ArrayList.java:457)
#     at com.example.service.ExportService.export(ExportService.java:45)
```

### 根因分析
```java
// 问题代码: 导出时查询所有数据
public void exportToExcel(HttpServletResponse response) {
    List<Data> allData = dataRepository.findAll();  // 100万条
    // 写入 Excel
    writeExcel(allData, response.getOutputStream());
}
```

### 解决方案
```java
// 方案1: 流式导出
public void exportToExcel(HttpServletResponse response) {
    try (SXSSFWorkbook workbook = new SXSSFWorkbook(100)) {  // 内存中保留100行
        Sheet sheet = workbook.createSheet();
        int rowNum = 0;
        
        // 分批查询
        int page = 0;
        int pageSize = 10000;
        List<Data> batch;
        
        do {
            batch = dataRepository.findByPage(page * pageSize, pageSize);
            for (Data data : batch) {
                Row row = sheet.createRow(rowNum++);
                writeRow(row, data);
            }
            page++;
        } while (!batch.isEmpty());
        
        workbook.write(response.getOutputStream());
    }
}

// 方案2: 使用 EasyExcel（阿里开源）
public void exportToExcel(HttpServletResponse response) {
    EasyExcel.write(response.getOutputStream(), Data.class)
        .sheet("数据")
        .doWrite(dataRepository::streamAll);  // 流式写入
}

// 方案3: 使用 Cursor 流式查询
@Transactional(readOnly = true)
public void exportToExcel(HttpServletResponse response) {
    try (Cursor<Data> cursor = dataRepository.cursorAll()) {
        // 流式处理
    }
}
```

## 案例12: 文件流未关闭导致内存泄漏

### 问题现象
- 服务运行一段时间后 OOM
- 文件操作频繁
- 堆中有大量未关闭的流对象

### 排查过程
```bash
# MAT 分析
# 查找未关闭的 InputStream/OutputStream
# 发现大量 FileInputStream 未关闭
```

### 根因分析
```java
// 问题代码: 文件流未关闭
public String readFile(String path) {
    FileInputStream fis = null;
    try {
        fis = new FileInputStream(path);
        byte[] data = new byte[fis.available()];
        fis.read(data);
        return new String(data);
    } catch (IOException e) {
        throw new RuntimeException(e);
    }
    // finally 中未关闭 fis
}

// 另一个问题: 异常时未关闭
public void writeFile(String path, String content) {
    FileOutputStream fos = new FileOutputStream(path);
    fos.write(content.getBytes());
    fos.close();  // 如果 write 抛异常，close 不会执行
}
```

### 解决方案
```java
// 方案1: 使用 try-with-resources（推荐）
public String readFile(String path) {
    try (FileInputStream fis = new FileInputStream(path);
         ByteArrayOutputStream baos = new ByteArrayOutputStream()) {
        byte[] buffer = new byte[1024];
        int len;
        while ((len = fis.read(buffer)) != -1) {
            baos.write(buffer, 0, len);
        }
        return baos.toString();
    } catch (IOException e) {
        throw new RuntimeException(e);
    }
}

// 方案2: 使用 NIO
public String readFile(String path) {
    return Files.readString(Path.of(path));
}

// 方案3: 使用 Apache Commons IO
public String readFile(String path) {
    return FileUtils.readFileToString(new File(path), StandardCharsets.UTF_8);
}
```

## 案例13: 线程泄漏导致 OOM

### 问题现象
- 服务运行几天后 OOM
- 线程数持续增长
- 最终无法创建新线程

### 排查过程
```bash
# 查看线程数量
jstack <pid> | grep "java.lang.Thread.State" | wc -l

# 或使用 arthas
thread

# 输出:
# Threads: 5000 active, 5 daemon
```

### 根因分析
```java
// 问题代码: 每次请求创建新线程
public void processAsync() {
    new Thread(() -> {
        // 处理任务
        processTask();
    }).start();  // 线程执行完后未销毁（线程池中）
}

// 另一个问题: 线程池未正确配置
ExecutorService executor = Executors.newCachedThreadPool();
// CachedThreadPool 会创建无限数量的线程
```

### 解决方案
```java
// 方案1: 使用有界线程池
ExecutorService executor = new ThreadPoolExecutor(
    10,                                      // 核心线程数
    50,                                      // 最大线程数
    60, TimeUnit.SECONDS,                    // 空闲线程存活时间
    new LinkedBlockingQueue<>(1000),         // 有界队列
    new ThreadPoolExecutor.CallerRunsPolicy() // 拒绝策略
);

// 方案2: 使用 Spring 异步
@Async("taskExecutor")
public CompletableFuture<Result> processAsync() {
    return CompletableFuture.completedFuture(process());
}

@Bean("taskExecutor")
public Executor taskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(10);
    executor.setMaxPoolSize(50);
    executor.setQueueCapacity(1000);
    executor.setThreadNamePrefix("async-");
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    return executor;
}

// 方案3: 监控线程数
@Scheduled(fixedRate = 60000)
public void monitorThreads() {
    ThreadMXBean threadMXBean = ManagementFactory.getThreadMXBean();
    int threadCount = threadMXBean.getThreadCount();
    if (threadCount > 1000) {
        log.warn("Thread count too high: {}", threadCount);
    }
}
```

## 案例14: 元空间溢出

### 问题现象
- 抛出 OutOfMemoryError: Metaspace
- 动态生成大量类
- 使用 CGLIB 或动态代理

### 排查过程
```bash
# 查看元空间使用
jstat -gcmetacapacity <pid>

# 查看类加载信息
jcmd <pid> VM.classloader_stats

# 查看类数量
jcmd <pid> VM.system_properties | grep "Loaded"
```

### 根因分析
```java
// 问题代码: 动态生成大量代理类
public class DynamicProxyGenerator {
    public Object createProxy(Class<?> targetClass) {
        Enhancer enhancer = new Enhancer();
        enhancer.setSuperclass(targetClass);
        enhancer.setCallback((MethodInterceptor) (obj, method, args, proxy) -> {
            return proxy.invokeSuper(obj, args);
        });
        return enhancer.create();  // 每次创建新的代理类
    }
}

// 每次调用都会生成一个新的 Class
// Class 卸载条件苛刻，导致元空间溢出
```

### 解决方案
```java
// 方案1: 缓存代理类
private static final Map<Class<?>, Object> PROXY_CACHE = new ConcurrentHashMap<>();

public Object createProxy(Class<?> targetClass) {
    return PROXY_CACHE.computeIfAbsent(targetClass, clazz -> {
        Enhancer enhancer = new Enhancer();
        enhancer.setSuperclass(clazz);
        enhancer.setCallback((MethodInterceptor) (obj, method, args, proxy) -> {
            return proxy.invokeSuper(obj, args);
        });
        return enhancer.create();
    });
}

// 方案2: 调整元空间大小
-XX:MetaspaceSize=256m
-XX:MaxMetaspaceSize=512m

// 方案3: 使用 JDK 动态代理代替 CGLIB
// Spring AOP 默认使用 JDK 动态代理
```

## 案例15: 堆外内存泄漏

### 问题现象
- 堆内存使用正常，但 RSS 持续增长
- 最终被 OOM Killer 杀死
- 使用 NIO 或 DirectByteBuffer

### 排查过程
```bash
# 查看 RSS（物理内存）
ps -p <pid> -o rss,vsz

# 查看堆外内存
jcmd <pid> VM.native_memory summary

# 使用 NMT（Native Memory Tracking）
-XX:NativeMemoryTracking=detail
```

### 根因分析
```java
// 问题代码: DirectByteBuffer 未释放
public void allocateDirectBuffer() {
    ByteBuffer buffer = ByteBuffer.allocateDirect(1024 * 1024);  // 1MB
    // 使用后未释放
    // DirectByteBuffer 不受 GC 直接管理
}

// 另一个问题: 使用 JNI 分配内存未释放
```

### 解决方案
```java
// 方案1: 使用 Cleaner 释放 DirectByteBuffer
public void allocateDirectBuffer() {
    ByteBuffer buffer = ByteBuffer.allocateDirect(1024 * 1024);
    try {
        // 使用 buffer
    } finally {
        // 手动释放（Java 9+）
        if (buffer.isDirect()) {
            ((sun.nio.ch.DirectBuffer) buffer).cleaner().clean();
        }
    }
}

// 方案2: 使用堆内存代替
ByteBuffer buffer = ByteBuffer.allocate(1024 * 1024);

// 方案3: 限制堆外内存大小
-XX:MaxDirectMemorySize=256m

// 方案4: 使用 arthas 查看
vmtool --action getInstances --className java.nio.DirectByteBuffer --limit 10
```

## 案例16: ThreadLocal 导致内存泄漏

### 问题现象
- 服务运行一段时间后内存持续增长
- 频繁 Full GC 但内存无法释放
- 堆中有大量 ThreadLocal 对象

### 排查过程
```bash
# MAT 分析堆转储
# 查找 ThreadLocal 实例
# 查看 ThreadLocalMap 中的 Entry

# Histogram:
# java.lang.ThreadLocal$ThreadLocalMap$Entry  500,000 个
# com.example.context.UserContext$1  500,000 个
```

### 根因分析
```java
// 问题代码: 线程池中使用 ThreadLocal 未清理
public class UserContext {
    private static final ThreadLocal<User> CURRENT_USER = new ThreadLocal<>();
    
    public static void setUser(User user) {
        CURRENT_USER.set(user);
    }
    
    public static User getUser() {
        return CURRENT_USER.get();
    }
    
    // 缺少 clear() 方法
}

// 在线程池中:
// 1. 线程 A 执行请求 1，设置 User 到 ThreadLocal
// 2. 线程 A 执行完请求，返回线程池
// 3. 线程 A 执行请求 2，ThreadLocal 中的 User 1 仍然存在
// 4. User 1 无法被 GC 回收
```

### 解决方案
```java
// 方案1: 使用后清理
public class UserContext {
    private static final ThreadLocal<User> CURRENT_USER = new ThreadLocal<>();
    
    public static void setUser(User user) {
        CURRENT_USER.set(user);
    }
    
    public static User getUser() {
        return CURRENT_USER.get();
    }
    
    public static void clear() {
        CURRENT_USER.remove();
    }
}

// 在 Filter 中清理
@Override
public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) {
    try {
        chain.doFilter(request, response);
    } finally {
        UserContext.clear();
    }
}

// 方案2: 使用 TransmittableThreadLocal（阿里开源）
// 支持线程池中正确传递
```

## 内存问题预防 Checklist

```
内存问题预防:

□ 代码审查:
  - 检查集合是否有大小限制
  - 检查流是否正确关闭
  - 检查 ThreadLocal 是否清理
  - 检查缓存是否有过期策略

□ 监控告警:
  - 堆内存使用率 > 80% 告警
  - 元空间使用率 > 80% 告警
  - 线程数超过阈值告警
  - GC 频率超过阈值告警

□ 配置优化:
  - 设置合理的堆大小
  - 设置元空间大小
  - 设置堆外内存大小
  - 配置 OOM 时 dump

□ 代码规范:
  - 使用 try-with-resources
  - ThreadLocal 必须清理
  - 缓存必须设置过期
  - 查询必须分页
```
