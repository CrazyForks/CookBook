## 案例43: Redis 缓存穿透

### 问题现象
- 数据库压力突然增大
- 大量请求直接打到数据库
- 缓存命中率下降

### 排查过程
```bash
# 查看 Redis 命中率
redis-cli INFO stats | grep keyspace
# keyspace_hits:1000
# keyspace_misses:50000

# 查看慢查询
redis-cli SLOWLOG GET 10

# 监控 Redis 请求
redis-cli MONITOR
```

### 根因分析
```
问题原因:
1. 查询不存在的数据
2. 缓存和数据库都没有
3. 每次请求都穿透到数据库

# 恶意攻击:
# 使用大量不存在的 ID 查询
# GET /api/user/999999999
```

### 解决方案
```java
// 方案1: 缓存空值
public User getUser(Long id) {
    String key = "user:" + id;
    String value = redisTemplate.opsForValue().get(key);
    
    if (value != null) {
        if ("NULL".equals(value)) {
            return null;  // 缓存的空值
        }
        return JSON.parseObject(value, User.class);
    }
    
    User user = userRepository.findById(id).orElse(null);
    if (user != null) {
        redisTemplate.opsForValue().set(key, JSON.toJSONString(user), 1, TimeUnit.HOURS);
    } else {
        redisTemplate.opsForValue().set(key, "NULL", 5, TimeUnit.MINUTES);  // 缓存空值
    }
    return user;
}

// 方案2: 布隆过滤器
@Autowired
private BloomFilter<Long> bloomFilter;

public User getUser(Long id) {
    if (!bloomFilter.mightContain(id)) {
        return null;  // 布隆过滤器判断不存在
    }
    // 查询缓存和数据库
}

// 方案3: 参数校验
@GetMapping("/api/user/{id}")
public User getUser(@PathVariable Long id) {
    if (id == null || id <= 0) {
        throw new IllegalArgumentException("无效的用户 ID");
    }
    return userService.getUser(id);
}
```

## 案例44: Redis 缓存雪崩

### 问题现象
- 大量缓存同时过期
- 数据库压力瞬间增大
- 服务响应超时

### 排查过程
```bash
# 查看 Redis 过期键
redis-cli INFO keyspace

# 查看数据库连接
SHOW STATUS LIKE 'Threads_connected';

# 查看慢查询
SHOW PROCESSLIST;
```

### 根因分析
```
问题原因:
1. 大量缓存设置相同的过期时间
2. 缓存服务重启
3. 缓存服务器故障

# 示例:
# 所有缓存设置 1 小时过期
# 1 小时后同时过期
# 数据库瞬间压力增大
```

### 解决方案
```java
// 方案1: 随机过期时间
public void setUserCache(User user) {
    String key = "user:" + user.getId();
    // 随机过期时间：1-2小时
    int expire = 3600 + new Random().nextInt(3600);
    redisTemplate.opsForValue().set(key, JSON.toJSONString(user), expire, TimeUnit.SECONDS);
}

// 方案2: 缓存预热
@PostConstruct
public void warmUpCache() {
    List<User> users = userRepository.findAll();
    for (User user : users) {
        redisTemplate.opsForValue().set("user:" + user.getId(), 
            JSON.toJSONString(user), 2, TimeUnit.HOURS);
    }
}

// 方案3: 使用本地缓存作为二级缓存
private final LoadingCache<Long, User> localCache = CacheBuilder.newBuilder()
    .maximumSize(10000)
    .expireAfterWrite(5, TimeUnit.MINUTES)
    .build(new CacheLoader<Long, User>() {
        @Override
        public User load(Long id) {
            return getUserFromRedis(id);
        }
    });

// 方案4: 熔断降级
@HystrixCommand(fallbackMethod = "getUserFallback")
public User getUser(Long id) {
    return getUserFromCache(id);
}

public User getUserFallback(Long id) {
    return new User();  // 返回默认值
}
```

## 案例45: Redis 内存溢出

### 问题现象
- Redis 报错 OOM
- 无法写入新数据
- 内存使用率 100%

### 排查过程
```bash
# 查看 Redis 内存使用
redis-cli INFO memory
# used_memory:10737418240
# maxmemory:10737418240

# 查看大 key
redis-cli --bigkeys

# 查看内存分布
redis-cli MEMORY DOCTOR
```

### 根因分析
```
问题原因:
1. 缓存数据量超过内存限制
2. 大 key 未清理
3. 内存碎片
4. 内存泄漏

# 常见大 key:
# - 大的 List/Set/Hash
# - 大的 String（序列化对象）
```

### 解决方案
```bash
# 方案1: 设置内存上限
# redis.conf
maxmemory 8gb
maxmemory-policy allkeys-lru  # LRU 淘汰

# 方案2: 清理大 key
# 扫描大 key
redis-cli --bigkeys

# 删除大 key（使用 UNLINK 异步删除）
UNLINK big_key

# 方案3: 数据压缩
# 使用压缩算法（snappy、lz4）

# 方案4: 分片
# 使用 Redis Cluster 分片存储
```

```java
// 方案5: 设置合理的过期时间
redisTemplate.opsForValue().set(key, value, 1, TimeUnit.HOURS);

// 方案6: 避免存储大对象
// 将大对象拆分为多个小对象
// 或使用 Hash 存储部分字段
```

## 案例46: MQ 消息堆积

### 问题现象
- 消息队列堆积大量消息
- 消费者处理不过来
- 业务延迟

### 排查过程
```bash
# 查看 RocketMQ 消息堆积
sh mqadmin consumerProgress -n localhost:9876 -g consumer-group

# 查看 Kafka 消息堆积
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group consumer-group

# 查看消费者状态
sh mqadmin consumerConnection -n localhost:9876 -g consumer-group
```

### 根因分析
```
问题原因:
1. 消费者处理速度慢
2. 消费者数量不足
3. 消费者异常退出
4. 消息量突增

# 常见场景:
# - 大促活动消息量突增
# - 消费者代码 Bug 导致异常
# - 依赖服务变慢
```

### 解决方案
```java
// 方案1: 增加消费者数量
// 部署多个消费者实例

// 方案2: 增加消费线程数
@Bean
public DefaultMQPushConsumer consumer() {
    DefaultMQPushConsumer consumer = new DefaultMQPushConsumer("consumer-group");
    consumer.setConsumeThreadMin(20);
    consumer.setConsumeThreadMax(50);
    consumer.setConsumeMessageBatchMaxSize(10);  // 批量消费
    return consumer;
}

// 方案3: 异步消费
@Override
public ConsumeConcurrentlyStatus consumeMessage(List<MessageExt> msgs, 
                                                 ConsumeConcurrentlyContext context) {
    // 异步处理
    CompletableFuture.runAsync(() -> processMessages(msgs));
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
}

// 方案4: 消费失败重试
@Override
public ConsumeConcurrentlyStatus consumeMessage(List<MessageExt> msgs, 
                                                 ConsumeConcurrentlyContext context) {
    try {
        processMessages(msgs);
        return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
    } catch (Exception e) {
        // 重试 3 次
        if (msgs.get(getReconsumeTimes()) < 3) {
            return ConsumeConcurrentlyStatus.RECONSUME_LATER;
        }
        // 进入死信队列
        return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
    }
}
```

## 案例47: MQ 消费失败

### 问题现象
- 消费失败率高
- 消息重试频繁
- 业务数据不一致

### 排查过程
```bash
# 查看消费失败消息
sh mqadmin queryMsgByOffset -n localhost:9876 -t topic -b 0 -o 100

# 查看重试队列
sh mqadmin topicStatus -n localhost:9876 -t %RETRY%consumer-group

# 查看死信队列
sh mqadmin topicStatus -n localhost:9876 -t %DLQ%consumer-group
```

### 根因分析
```java
// 问题代码: 消费逻辑异常
@Override
public ConsumeConcurrentlyStatus consumeMessage(List<MessageExt> msgs, 
                                                 ConsumeConcurrentlyContext context) {
    for (MessageExt msg : msgs) {
        Order order = JSON.parseObject(msg.getBody(), Order.class);
        processOrder(order);  // 可能抛出异常
    }
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
}

// 常见失败原因:
// - 数据库连接失败
// - 依赖服务不可用
// - 消息格式错误
// - 业务逻辑异常
```

### 解决方案
```java
// 方案1: 捕获异常并记录
@Override
public ConsumeConcurrentlyStatus consumeMessage(List<MessageExt> msgs, 
                                                 ConsumeConcurrentlyContext context) {
    for (MessageExt msg : msgs) {
        try {
            Order order = JSON.parseObject(msg.getBody(), Order.class);
            processOrder(order);
        } catch (Exception e) {
            log.error("消费失败: {}", msg.getMsgId(), e);
            // 记录失败消息，后续人工处理
            saveFailedMessage(msg, e);
        }
    }
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
}

// 方案2: 幂等消费
@Override
public ConsumeConcurrentlyStatus consumeMessage(List<MessageExt> msgs, 
                                                 ConsumeConcurrentlyContext context) {
    for (MessageExt msg : msgs) {
        String msgId = msg.getMsgId();
        // 检查是否已消费
        if (isConsumed(msgId)) {
            continue;
        }
        try {
            processMessage(msg);
            markConsumed(msgId);
        } catch (Exception e) {
            log.error("消费失败: {}", msgId, e);
            return ConsumeConcurrentlyStatus.RECONSUME_LATER;
        }
    }
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
}
```

## 案例48: Nginx 502 Bad Gateway

### 问题现象
- 返回 502 错误
- 后端服务不可用
- Nginx 无法连接上游

### 排查过程
```bash
# 查看 Nginx 错误日志
tail -f /var/log/nginx/error.log

# 输出:
# upstream prematurely closed connection while reading response header from upstream

# 查看后端服务状态
curl http://backend-server:8080/health

# 查看 Nginx 配置
nginx -t
```

### 根因分析
```
问题原因:
1. 后端服务宕机
2. 后端服务端口错误
3. 后端服务超时
4. Nginx 与后端网络不通

# 常见场景:
# - 后端服务 OOM 被杀
# - 后端服务端口被占用
# - 防火墙规则
```

### 解决方案
```nginx
# 方案1: 检查后端服务
# 确保后端服务正常运行
systemctl status backend-service

# 方案2: 配置健康检查
upstream backend {
    server 127.0.0.1:8080 max_fails=3 fail_timeout=30s;
    server 127.0.0.1:8081 max_fails=3 fail_timeout=30s;
}

# 方案3: 增加超时时间
proxy_connect_timeout 60s;
proxy_send_timeout 60s;
proxy_read_timeout 60s;

# 方案4: 配置重试
proxy_next_upstream error timeout http_502 http_503;
proxy_next_upstream_tries 3;
```

## 案例50: Feign 调用超时

### 问题现象
- Feign 调用报错 timeout
- 依赖服务响应慢
- 线程池耗尽

### 排查过程
```bash
# 查看 Feign 日志
logging.level.com.example.feign=DEBUG

# 输出:
# [UserService#getUser] ---> GET http://user-service/api/user/1 HTTP/1.1
# [UserService#getUser] <--- HTTP/1.1 200 (5000ms)

# 查看线程堆栈
jstack <pid> | grep "feign"
```

### 根因分析
```yaml
# 问题配置: 超时时间过短
feign:
  client:
    config:
      default:
        connectTimeout: 1000
        readTimeout: 1000  # 1秒

# 依赖服务处理时间 > 1秒
# 导致超时
```

### 解决方案
```yaml
# 方案1: 增加超时时间
feign:
  client:
    config:
      default:
        connectTimeout: 5000
        readTimeout: 10000
      user-service:  # 特定服务配置
        connectTimeout: 10000
        readTimeout: 30000

# 方案2: 配置重试
feign:
  client:
    config:
      default:
        connectTimeout: 5000
        readTimeout: 10000
  hystrix:
    enabled: true

# 方案3: 使用 Hystrix 熔断
@FeignClient(name = "user-service", fallbackFactory = UserClientFallback.class)
public interface UserClient {
    @GetMapping("/api/user/{id}")
    User getUser(@PathVariable Long id);
}

@Component
public class UserClientFallback implements FallbackFactory<UserClient> {
    @Override
    public UserClient create(Throwable cause) {
        return id -> {
            log.error("Feign 调用失败", cause);
            return new User();  // 返回默认值
        };
    }
}
```

```java
// 方案4: 使用 Sentinel 限流降级
@FeignClient(name = "user-service")
public interface UserClient {
    @GetMapping("/api/user/{id}")
    @SentinelResource(value = "getUser", fallback = "getUserFallback")
    User getUser(@PathVariable Long id);
    
    default User getUserFallback(Long id, Throwable e) {
        log.error("Feign 调用失败", e);
        return new User();
    }
}
```
